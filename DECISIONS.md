# Decisions

Every decision taken while building this project that a reader might otherwise
have to reverse-engineer, with the reasoning behind it. Written in the order
the decisions came up.

---

## 1. Architecture and runtime

### 1.1 `@opennextjs/cloudflare`, not Pages / next-on-pages

Fixed by the brief. Worth recording why it matters in practice: the worker gets
real bindings (`DB`, `PHOTOS`, `RATE_LIMIT`) through `getCloudflareContext()`,
so route handlers and server components talk to D1 and R2 directly with no
network hop and no separate API tier.

### 1.2 No R2 incremental cache

The OpenNext template provisions an R2 bucket for the Next.js incremental
cache. Every page in this app is per-user and authenticated, so there is
nothing cacheable to put in it. `open-next.config.ts` therefore calls
`defineCloudflareConfig()` with no overrides, which removes one Cloudflare
resource the user would otherwise have to create before the first deploy.

### 1.3 `nodejs_compat` is enabled

Required by `@opennextjs/cloudflare` itself — the Next.js server runtime it
bundles needs it. Application code does not use Node-only APIs: binary data is
handled with `ArrayBuffer`/`Uint8Array` and base64 goes through `btoa`
(`lib/base64.ts`), never `Buffer`.

`global_fetch_strictly_public` is also set, so a `fetch()` to our own hostname
goes out to the public internet instead of looping back inside the worker.

### 1.4 No `next/font/google`

Fonts are a system stack ending in `PingFang TC` / `Noto Sans TC` /
`Microsoft JhengHei`. `next/font/google` downloads font files at build time,
which makes the build depend on network access; a CJK-aware system stack costs
nothing to load and renders Traditional Chinese correctly on every platform.

### 1.5 shadcn/ui components are vendored, not installed by its CLI

`ui.shadcn.com` is unreachable from the build environment (the egress policy
returns 403 for it), so `npx shadcn init` cannot run. The components in
`components/ui/` are therefore written directly against the `radix-ui`
primitives, which come from npm. They follow shadcn's "new-york" conventions —
`cn()`, `data-slot` attributes, CVA variants, the same OKLCH token names — so
`npx shadcn add <component>` will drop in alongside them unchanged once the
registry is reachable.

### 1.6 `cloudflare-env.d.ts` is generated, not committed

`wrangler types` emits ~15k lines of workerd runtime types. Committing that
buries real changes in review noise, so it is git-ignored and regenerated by a
`postinstall` script. Secrets are not in `wrangler.jsonc`, so `wrangler types`
cannot see them; `types/env.d.ts` declaration-merges them into `CloudflareEnv`
so server code still gets type safety for them.

## 2. Data layer

### 2.1 Isolation is enforced in one place and checked mechanically

D1 has no row level security, which makes cross-user isolation the highest-risk
part of this project: a single query that forgets its `userId` predicate leaks
another person's library, silently, with no error anywhere.

The design assumes that reviewers and future contributors will forget, so it
does not rely on discipline:

1. `db/repositories/books.ts` and `db/repositories/scans.ts` are the only files
   allowed to touch the database. Every exported function takes `userId` as its
   first parameter and every statement — select, update, delete — is scoped by
   it.
2. `scripts/check-isolation.ts` parses those files with the TypeScript compiler
   API and fails the build on an unscoped statement, a wrong first parameter, or
   an insert that does not set `userId`. It also fails if anything under `app/`
   or `components/` imports the db client, Drizzle, or the schema.
3. `db/repositories/books.test.ts` and `scans.test.ts` create two users and
   assert that every read, write and delete path returns nothing and changes
   nothing across the boundary.
4. `e2e/isolation.spec.ts` checks the same property from outside, through the
   running app: the list, a direct URL to another user's book id, two concurrent
   browser sessions, and an anonymous visitor.

The checker was verified by breaking the code on purpose — removing a `userId`
predicate, reordering a signature, and adding a db import to `app/` — and
confirming it failed each time.

### 2.2 `lib/data/` binds the request's database handle

The brief requires that nothing in `app/` or `components/` imports the db
client. Repository functions take `(userId, db, …)` so tests can hand them a
database, which leaves route handlers with no way to supply one.

`lib/data/books.ts` and `lib/data/scans.ts` re-export each repository function
with the request's D1 binding already applied, keeping `userId` as the first
argument. This is the only bridge between the two, and it means UI code
_cannot_ obtain an unscoped database handle even by accident.

`iterateBooks` is written out by hand rather than bound, because it returns an
async generator: wrapping it in an async function would produce a promise of a
generator, which `for await` cannot consume.

### 2.3 JSON columns for `authors` and `categories`

SQLite has no array type. Both are stored as JSON text
(`text({ mode: "json" }).$type<string[]>()`), and the repository decodes them on
the way out so the encoding never reaches the UI. The decoder is defensive
rather than trusting the type: a row written by a raw SQL seed or an older
client could hold anything, so a bare string becomes a single-element array and
anything unparseable becomes an empty one.

### 2.4 Search escapes LIKE wildcards explicitly

Drizzle's `like()` helper emits no `ESCAPE` clause, so a user searching for
`100%` would have matched every row. `db/repositories/books.ts` builds the
pattern itself and appends `ESCAPE '\'`. There is a test for exactly this.

### 2.5 The unique index on ISBN is partial

`unique(userId, isbn13) where isbn13 is not null`. Without the partial
predicate, a second book with no ISBN would collide with the first, because
SQLite treats NULLs as distinct in a unique index only for the _whole_ row.
Two different users holding the same ISBN is fine and is covered by a test.

### 2.6 Migrations are ordered by foreign-key dependency

`drizzle-kit` emits `CREATE TABLE` statements alphabetically, which would have
created `books` before `scans` and `user`. SQLite tolerates a forward reference,
but relying on that is fragile, so `drizzle/0000_init.sql` is reordered to
`user → session/account/verification → scans → books`. The snapshot does not
record statement order, so future `generate` runs are unaffected.

## 3. Authentication

### 3.1 Google OAuth and email OTP, no passwords

Both are required by the brief. `emailAndPassword` is left disabled: with OTP
and Google available there is no reason to store password hashes at all.
Account linking is enabled for both providers so signing in with Google and
with the same address by OTP lands on one account.

### 3.2 The better-auth CLI trails the library, so the schema is verified

`@better-auth/cli`'s latest release (1.4.21) is behind the installed
`better-auth` (1.7.1), and its generated schema omitted `account.issuer`, which
the runtime requires. Sign-in would have failed at runtime with no build-time
warning.

`db/auth-schema.ts` is generated by the CLI and then patched, and
`scripts/check-auth-schema.ts` diffs the Drizzle tables against
`getAuthTables(auth.options)` — what the installed runtime actually queries —
and fails `npm run lint` on any drift. It matches tables by _export name_, not
SQL table name, because that is how the Drizzle adapter resolves a model
(better-auth's `rateLimit` model lives in the `rate_limit` table).

### 3.3 A complete KV secondary storage, written here

`better-auth-cloudflare`'s `createKVStorage` implements only `get`/`set`/
`delete`. better-auth 1.7 also requires `getAndDelete` and `increment`, so
every `/api/auth/*` request failed. `lib/auth/kv-storage.ts` implements the full
interface.

### 3.4 better-auth's rate limiting uses D1, not KV

KV has no atomic increment and no read-after-write consistency, so a KV-backed
counter is trivially raced. better-auth supports `storage: "database"`, which
puts the counters in D1 where they can be counted correctly. Sending an OTP is
capped harder than other endpoints (5/min vs 100/min) because each one costs an
email.

The `increment` method in `lib/auth/kv-storage.ts` is still implemented, for
interface completeness, with a comment saying it is best-effort and that
nothing relies on it.

### 3.5 `BETTER_AUTH_URL` is the base URL, not the request

better-auth rejects a request whose `Origin` header does not match its base URL.
The obvious fix on Workers is to derive the base URL from `request.url`, which
Cloudflare sets from its own routing — but under OpenNext the request URL is
normalised to the configured host before a route handler sees it, so it cannot
identify the origin the client actually used. (This was found by an e2e test
failing with `INVALID_ORIGIN`; every browser request was being refused.)

`BETTER_AUTH_URL` is therefore the single source of truth, and
`TRUSTED_ORIGINS` takes a comma-separated list for preview deployments or a
second custom domain. **This must match the origin users actually visit** — it
is the most likely thing to get wrong on first deploy.

### 3.6 Email delivery is optional

Workers have no built-in outbound email. `lib/auth/send-otp.ts` posts to
Resend's HTTP API when `RESEND_API_KEY` is set, and otherwise logs the code with
a warning. That keeps the login flow usable in local development without
provisioning an email provider, and makes the production requirement explicit
rather than silent. `RESEND_API_KEY` and `OTP_FROM_EMAIL` are optional extras
beyond the brief's secret list.

### 3.7 The config-only auth instance lives in its own module

The better-auth CLI needs an `auth` export built without bindings. Keeping it in
`lib/auth/index.ts` meant every request also constructed that binding-less
instance and warned about a missing secret. It moved to `lib/auth/cli.ts`.

## 4. Photos and R2

### 4.1 Upload goes through the worker, not a presigned PUT

The brief allows either. Server-side upload was chosen because:

- The `PHOTOS` binding already exists in the worker; a presigned PUT needs R2
  S3-API credentials as two more secrets, plus a CORS policy on the bucket.
- The 10MB cap means the request fits comfortably through a worker.
- Validation (type, size, non-empty) and the `scans` row are then written in one
  place, in one request, and cannot get out of step. With a presigned PUT the
  client could upload and never tell the server, leaving orphaned objects.

The trade-off is that the bytes pass through the worker. At this size that costs
little, and it can be swapped later without touching the client contract.

### 4.2 Object keys embed the owner

`{userId}/{scanId}.{ext}`. Ownership is visible in the key, `deleteUserPhotos`
becomes a prefix list-and-delete, and `keyBelongsToUser()` gives the photo route
a second check independent of the database. The bucket has no public access.

### 4.3 The photo route answers 404 for everything

Not signed in, someone else's scan, missing scan, missing object — all 404.
A 403 would confirm that a given scan id exists, which is exactly what an
attacker enumerating ids wants to know.

## 5. Recognition

### 5.1 Raw `fetch`, not the Anthropic SDK

Required by the brief, and independently correct here: the worker bundle carries
no SDK dependency, and the request is a single POST that is easy to read and to
test with an injected `fetchImpl`.

### 5.2 `claude-sonnet-4-5`

Fixed by the brief. (Current Anthropic guidance would default to a newer model;
the brief names this one explicitly, so it is used as specified. Changing it is
a one-line edit in `lib/vision.ts`.)

### 5.3 Forced tool use, not "reply in JSON"

`tool_choice: {type: "tool", name: "record_books"}` makes the reply a structured
object validated against a schema. Asking for JSON in prose means parsing
whatever comes back, including markdown fences and preamble. `strict: true` is
deliberately _not_ sent, since it is not documented as supported on this model
tier; the parser validates every field itself instead, which it would have to do
regardless.

### 5.4 Asynchronous by construction

`POST /api/scan` marks the scan and returns `202` immediately, with the work
running under `ctx.waitUntil`; the client polls `GET /api/scan/[id]`. One
recognition call plus a Google Books lookup per book routinely exceeds what a
request should be held open for, so this is not a fallback for when the
synchronous path is too slow — there is no synchronous path.

Cloudflare Queues would be the next step if a scan ever needed to survive a
worker eviction or be retried without the client asking. `waitUntil` is enough
here and needs no extra resource.

### 5.5 What "needs review" means

A book is flagged when the model's self-assessed confidence is below 0.6, **or**
when Google Books returned nothing. The second case matters as much as the
first: a confident reading that no catalogue can corroborate is exactly the one
worth a human glance.

### 5.6 Google Books wins on bibliographic fields, but only where it has data

A catalogue entry beats a guess made from a photographed spine, so the lookup
overrides title, authors and publisher — but a sparse record never erases what
was legible on the cover. The `country=TW` parameter is always sent: without it
Google rejects unauthenticated requests from a datacenter.

A failed lookup returns `null` rather than throwing, so a Google outage
degrades enrichment instead of failing the whole scan.

### 5.7 Retry policy

Two retries with exponential backoff on 429, 5xx and network errors. A 4xx is
not retried — it will not change. Malformed JSON in a 200 is not retried either,
and is stored on the scan verbatim so a bad response can be inspected after the
fact.

### 5.8 Client-side compression, and what happens to HEIC

Photos are resized to 2048px on the longest side and re-encoded as JPEG at
quality 0.85 before upload. This cuts upload time and keeps the payload well
inside the Messages API's 5MB per-image limit.

HEIC is accepted by the upload endpoint (the brief asks for it) but the
Messages API does not support it. In practice the browser converts it to JPEG
during compression. When a browser cannot decode HEIC at all, `createImageBitmap`
rejects and the user gets "你的瀏覽器無法讀取這張圖片，請改用 JPEG 或 PNG" rather
than a confusing server-side failure later.

### 5.9 Books are written before the user confirms them

The review screen edits and deletes existing rows. Writing them first is what
lets the worker finish and the browser poll for a result; holding them in memory
would mean losing the scan if the tab closed. Anything the user unticks is
deleted on confirm.

## 6. Library UI

### 6.1 Filtering happens in the browser

The whole library is loaded once by the server component and filtered, searched
and sorted in memory. A personal shelf is small enough that this makes search
feel instant, and the 300ms debounce exists only to stop the list re-sorting on
every keystroke rather than to save a round trip.

This is the right trade at personal-library scale. At tens of thousands of books
it would need to move server-side; the repository already supports `filter`,
`search`, `sort`, `limit` and `offset`, so that change is confined to one
component.

### 6.2 Optimistic updates with explicit rollback

A purchase toggle flips immediately and restores the _previous values_ — both
`isPurchased` and `purchasedAt` — if the server rejects it, with a toast saying
why. Batch operations snapshot the whole list and restore it wholesale.

### 6.3 Server actions re-derive the user

No action trusts a user id from the client. Each calls `requireUserId()` and
then goes through `lib/data`, so a caller passing someone else's book id simply
affects zero rows and gets "找不到這本書".

### 6.4 Covers use plain `<img>`

Cover URLs are third-party Google hosts. Routing them through the Next image
optimizer would mean an allow-list per host and paying to proxy every thumbnail,
for images that are already small. `BookCover` falls back to a typographic tile
when there is no cover, so the grid never shows a broken image.

## 7. CSV export

### 7.1 Written for Excel

UTF-8 BOM (Excel does not detect UTF-8 without it, and Chinese becomes
mojibake), CRLF line endings per RFC 4180, `是`/`否` for the purchase flag, and
timestamps in Asia/Taipei so a file exported from an edge node in Frankfurt
reads the same as one exported in Taipei.

### 7.2 Streamed, not assembled

`createCsvStream` takes an async iterable and the repository pages through D1,
so the worker never holds the whole library in memory. Cancelling the download
closes the generator and stops the paging; a database error surfaces on the
stream instead of silently truncating the file.

### 7.3 The escaping tests use an independent parser

`lib/csv.test.ts` implements its own RFC 4180 reader and asserts round-trips
through it, rather than comparing against an expected string. A string
comparison only proves the writer does what it did yesterday; a parser proves
the file can actually be read back. Verified again at 1020 rows against the
running worker with Python's `csv` module.

### 7.4 Formula injection is not neutralised

A title beginning `=`, `+`, `-` or `@` will be treated as a formula by Excel.
The usual mitigation is to prefix such values with a quote, which corrupts the
data and breaks round-tripping. Since users export their own library and the
brief asks for a faithful export, the values are written as-is. Worth
revisiting if exports are ever shared between accounts.

## 8. Engineering

### 8.1 Tests run inside workerd

`@cloudflare/vitest-pool-workers` runs the repository and pipeline tests against
a real local D1, applying the same migrations that ship. A mocked database would
not have caught the `LIKE ESCAPE` bug, the partial-index behaviour, or the
timestamp mode round-trips.

`vitest.config.mts` uses the `.mts` extension because Vite loads the config as
CommonJS otherwise and `@cloudflare/vitest-pool-workers` is ESM-only.

### 8.2 What is mocked, and what is not

Only the two outbound HTTP services (Anthropic, Google Books) are faked, through
an injected `fetchImpl`. D1, R2 and KV are the real local implementations that
miniflare provides. `lib/scan-pipeline.test.ts` mocks `getDb` and `getPhoto`
only because they resolve their binding through the OpenNext request context,
which does not exist outside a worker request.

### 8.3 e2e tests authenticate once

The suite signs both seeded users in through the real login form in a setup
project and reuses the saved storage state. Logging in per test tripped the
app's own OTP rate limit partway through the run — the limit working as
designed. The one-time code is read from the KV namespace the app wrote it to,
through wrangler's local explorer API, so nothing test-specific exists in the
application itself.

### 8.4 `npm run lint` is more than ESLint

It runs ESLint, `tsc --noEmit`, the isolation checker and the auth schema
checker. A green lint therefore means types, the isolation invariant and the
auth schema are all verified, not just formatting.
